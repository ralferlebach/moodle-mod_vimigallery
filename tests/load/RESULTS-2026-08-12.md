# mod_vimigallery — load test results, 2026-08-12

Album of 100 maps × 150 nodes (~20 KB per map), one comment per map, upload
source. 25 concurrent users fetching maps through `mod_vimigallery_get_item`.
JMeter ran ~90 s, k6 60 s.

## Headline

**Both runs clean: zero exceptions, zero non-200 in 46 436 requests.** The lazy
item fetch introduced in 0.3.1 does what it was built for.

| | JMeter | k6 |
| --- | --- | --- |
| Requests | 21 631 | 24 805 |
| Throughput | 239.9/s | 405.3/s |
| Errors | 0 (0.00 %) | 0 (0.00 %) |
| Mean | 95 ms | 61 ms |
| p95 | — | 102 ms |
| Max | 429 ms | 3 340 ms |

## The number that matters: response size is flat

```
vimigallery_item_bytes: avg=20 006  min=19 870  med=20 021  max=20 022  p95=20 021
```

Minimum and maximum differ by **152 bytes across 24 805 fetches**. Every fetch
ships exactly one map and nothing else — no album metadata, no comment payload,
no growth with the album size. That is the direct measurement that the lazy path
is not re-doing per-album work on each request, and it is what the old design
could not have produced: before 0.3.1 the whole album went into one page.

For comparison, the same album rendered eagerly would have put ~2 MB of map JSON
into a single HTML response; now the page carries ~20 KB and each further map
costs one 20 KB fetch that only happens if the reader actually swipes to it.

## Latency

`get_item` is **fast and tight**: median 55 ms, p90 91 ms, p95 102 ms. Compared
with `mod_vimipad`'s `get_workspace` (median 281 ms, p95 550 ms) this is roughly
5× cheaper per call, which is the expected shape — one materialised map read by
id versus a whole workspace assembled from three tables.

5 of 24 805 calls (0.02 %) exceeded the 2000 ms budget, with a 3.34 s maximum.
That is a 33× outlier over the p95 and the same pattern seen in the vimipad run,
so the likely explanation is the same: cold cache or dev-box contention rather
than anything in the query path. Worth confirming once with a p99 and a check of
whether the slow calls cluster at the start of the run.

## Throughput degradation under JMeter is worth a note

JMeter's summariser shows throughput falling across the run:

```
348/s (first 24 s) → 251/s → 156/s → 154/s
```

with mean latency rising 53 ms → 97 ms → 156 ms → 162 ms. k6, which ran a shorter
and steadier profile, showed no equivalent drift.

This is most likely the dev host warming up in the wrong direction — PHP opcache
and MariaDB buffers competing with JMeter's own JVM on the same machine — rather
than a leak in the plugin, because the k6 run at higher throughput (405/s) stayed
flat. But it is the one thing here I would not call fully explained, and the cheap
check is to run JMeter alone against a longer duration and see whether the curve
flattens or keeps falling.

## Comparison with the vimipad run

| | vimipad `get_workspace` | gallery `get_item` |
| --- | --- | --- |
| median | 281 ms | 55 ms |
| p95 | 550 ms | 102 ms |
| payload | whole map (1000 nodes) | one map (150 nodes) |

Not a like-for-like comparison — different payload sizes — but it confirms the
architectural point: paying for one map at a time is cheap, and the gallery never
has to pay for the whole album at once.

## Reproducing

```
make load-seed ITEMS=100 NODESPERMAP=150
make jmeter           # or: make load-k6
```

The useful next experiment is a size sweep: `ITEMS=500` should leave
`vimigallery_get_item` and `vimigallery_item_bytes` unchanged. If either climbs
with `ITEMS`, the lazy path has regressed into resolving the whole album per
fetch. Pointing the gallery at a `live` quiz or database source instead measures
the source adapter, which is the other thing worth knowing.
